# milstart — 업무 시작

각자 PC에서 같은 모양으로 쓰는 시작 루틴이다. 순서대로 한다. 이 대화창은 **총괄 대화창**이라 저장소를 고치지 않는다 — 고치는 일은 모두 milwork 작업 대화창으로 넘긴다.

## 「나」는 누구인가
`git config vcc.me`(원우|민지|미리). 없으면 `user.name`·`user.email`에 든 글자로 짐작한다(`.claude/skills/milwork/board.py`의 `who_am_i()`와 같은 방식). 모르면 한 번 묻고 `git config vcc.me <이름>`을 권한다. 이 글의 「나」는 이 사람이고, 「**미리만**」 표시가 붙은 절은 `vcc.me`가 미리일 때만 한다(PR 병합·작업내역서·작업일지 같은 팀 총괄 일). 상태판·큐·결정은 사람별 파일(`board-<이름>.md`)이며 `board.py`가 자동으로 내 파일을 쓴다. 담당 검사는 CLAUDE.md 「누가 무엇을 고치나」를 나 기준으로 본다. 다른 사람에게 보낼 요청은 PR 본문 「## 팀원에게」로 한다.

## 1. 상태 확인 (조용히, 문제 있을 때만 말한다)
- 본 폴더: `git -C C:/dev/VCC fetch -q` → `git -C C:/dev/VCC status -sb`. main이 아니거나 `[behind n]`이면 hook과 같은 모양의 한 줄을 **보고 맨 위에** 보여 준다: `[VCC] pull 안 됨 — <이유: 다른 브랜치 x / n커밋 뒤처짐 / 고친 파일 있음> · 직접 pull하세요: git -C C:/dev/VCC pull`. 대신 pull하거나 되돌리지 않는다(남의 작업일 수 있다).
- `.env`: **값을 읽거나 출력하지 않는다.** 키 이름 3개(CLOVA_KEY·ANTHROPIC_API_KEY·VCC_LOGIN_PW)가 있는지만 본다. 모자라면 "Bitwarden에서 다시 붙여 주세요"라고만 말한다(.env 편집은 내가 직접 한다).
- 총괄 등록: `ListAgents` 첫 줄 「This session is <이름>」에서 내 세션 이름을 읽어 `python -X utf8 C:/dev/VCC/.claude/skills/milwork/board.py chief --set <내 세션이름>`으로 내 상태판 머리에 적는다(작업창이 제안·결정요망을 이 이름으로 보낸다).
- **「컴퓨터 바꿨어」인 날만**: 스킬 연결(`~\.claude\skills`에 milstart·milend·milreview·milwork·milwatch가 모두 있는지, 빠지면 `.claude/미리-PC설정.md` 2절대로 junction — SymbolicLink는 관리자 권한이 필요하니 쓰지 않는다)과 계정(`gh auth status` 활성 계정, `git -C C:/dev/VCC config user.email`이 noreply 주소인지, 나=미리면 활성 계정이 hufsiei)을 본다. 다르면 알린다.
- 남은 작업 폴더(`C:\dev\VCC-*`): `python -X utf8 C:/dev/VCC/.claude/skills/milwork/board.py list`로 내 상태판(드라이브 `@VCC\총괄\board-<이름>.md`)과 함께 본다. 줄마다 어느 작업·어느 상태인지 그대로 보고하고, 「폴더 없음」 줄은 `prune`, 「상태판에 없음」 폴더는 병합됐으면 지우고 아니면 `add`로 적을지 묻는다. 「전달 대기」가 있으면 ③ 「팀원과 맞춰야 할 일」에 넣는다.

## 2. 자료 모으기
- **미리만** 작업내역서: `H:\내 드라이브\@VCC\@VCC작업내역 v6.xlsx` (openpyxl, data_only, 읽기만). 시트 `작업목록`(번호·시기·단계·담당·기한·진행상황·비고·선행·막힌 점), `전달사항`(처리상태가 확인완료가 아닌 것), `주요링크`. 나=원우·민지면 이 파일을 건드리지 않고, 내 담당 작업은 `docs/tasks.json`·git 기록·PR 본문으로 본다.
- git: 최근 병합 PR(`gh pr list -R hufsiei/VCC --state merged --limit 20`), 열린 PR, `git log --since` 어제.
- 외부 요인: 메모리의 NCP 크레딧 상태 등.

## 3. 보고 (기술 용어 최소, 개념·의미 중심)
아래 세 부분만, 짧게.

**① 전체 흐름에서 어디까지 왔나** — 시기 단계(개발 1주 → 2주 → 통합 → 리허설 → 본선)별 완료 비율 표 1개(미리: 작업내역서 기준. 그 밖: 내 담당 작업 기준) + 지금 단계의 의미 한두 문장. 예: "학생 쪽 기능이 서버까지 이어졌고, 이제 화면이 실제 서버를 쓰게 바꾸는 단계예요."

**② 정체된 곳** — 기한이 지났는데 진행중·시작 전인 일, 선행 작업에 막힌 일, 외부 요인(NCP 크레딧 등)에 묶인 일. 각 항목에 "그래서 무엇이 늦어지나"를 한 줄로.

**③ 오늘 내가 할 일 3~5개** — 무엇을·왜. 세 묶음으로:
- 제가 혼자 할 수 있는 일(내 개입 없음)
- 팀원과 맞춰야 할 일(누구와, 무엇을 — PR 본문 「팀원에게」로 보낼 것)
- 내가 결정할 일(선택지와 추천)

기술적인 세부는 내가 따로 상의하므로 여기서 풀지 않는다.

## 4. 혼자 할 수 있는 일 → 큐에 넣고 milwork 지시문으로 남기기
**직접 시작하지 않는다.** 먼저 「제가 혼자 할 수 있는 일」마다 `board.py queue add --task "<작업번호 또는 –> <제목>" --files a,b --from milstart`로 큐에 넣어 `Q-n`을 받는다. **「고칠 곳」이 나의 담당 파일인지** CLAUDE.md로 먼저 본다. 남의 담당이면 큐에 넣지 말고 그 사람에게 보낼 요청으로 돌린다.

**넣은 일은 바로 승인한다**(11/25): `queue add` 바로 뒤에 `board.py queue approve Q-n`. milstart가 고른 일은 내가 블록을 새 창에 붙여 넣는 것 자체를 승인으로 치므로, 새 창은 엔터만 치면 milwork의 `queue take`를 지나 바로 시작한다. approve가 **종료코드 2(겹침)**를 내면 그 일은 「제안」으로 남으니 **지시문을 주지 않고**, 출력된 겹친 줄(어느 작업·파일과 겹치는지)을 보고 ② 정체된 곳(앞 작업이 끝나야 시작) 또는 ③ 「내가 결정할 일」(합칠지·순서를 바꿀지)에 올린다. 작업 창이 `--from 파생`으로 넣는 파생업무는 이 규칙과 상관없이 총괄의 `[승인 Q-n]`을 기다린다.

그다음 보고 뒤에 새 대화창에 그대로 붙여 넣을 지시문을 코드 블록 하나씩으로 쓰고, **블록 위에 `Q-n · <모델> · <effort>`를 붙여 보여 준다**(지시문 첫 줄 끝에도 `Q-n`). 새 창을 열 때 모델을 먼저 고르고 블록을 붙여 넣으라는 뜻이다. 한 블록 = 한 작업 = 한 대화창. 형식:

````
```
milwork <나> <슬러그> <작업 제목> (작업 N) Q-n

모델: <모델> · <effort> (<고른 이유 한 마디>)
목표: <끝났을 때 무엇이 달라지나, 한두 줄>
왜: <오늘 이 일을 하는 이유 — 무엇을 풀거나 무엇의 선행인가>
고칠 곳(예상): <파일·폴더>
완료 기준: <시험·확인 방법. 예: functions/test_x.py 통과, 390px 화면 확인>
주의: <담당 경계, AI 비용(호출 수·예상 금액), 건드리지 말 것>
```
````

- `<나>`는 위에서 정한 이름(원우|민지|미리). 작업내역서 번호가 없으면 `(작업 N)`은 뺀다. 제목은 짧고 구체적으로.
- **모델 고르기**(11/25): 작업내역서 「모델」 열(**미리만** 봄)에 값이 있으면 그대로 따른다. 없으면(원우·민지는 늘) 단순 편집은 Sonnet 5.5, 판단·검사(검토·측정 해석·규칙 대조)는 Opus 5.5, 여러 파일을 잇는 일(서버+화면+시험 함께)은 Fable 5.2. effort는 low · medium · high 중 하나로, 한 파일 몇 줄이면 low, 보통 medium, 설계를 함께 정하면 high. 블록 위 줄과 블록 안 「모델:」 줄은 같은 값으로 쓴다. 예: `Q-3 · Sonnet 5.5 · medium` / `모델: Sonnet 5.5 · medium (스킬 문서 한 곳에 규칙 두 개 더하기)`.
- **슬러그**(11/25): 영문 소문자 2~3단어를 하이픈으로(예: `cloud-harden`). milwork가 이것을 그대로 폴더(`C:\dev\VCC-<슬러그>`)·브랜치(`<나 영문 접두>/<슬러그>`, milwork 규칙대로)로 쓰고, 대화창 제목도 첫 줄에서 나오므로 **창 이름 = 폴더 이름**이 된다. 상태판에 이미 있는 폴더와 겹치지 않게 고른다. 보고·밀리뷰·밀종료에서 작업을 가리킬 때도 이 슬러그로 부른다(예: 「`cloud-harden`(진입점 다듬기) PR #218」).
- 「고칠 곳」이 다른 지시문과 겹치면 하나로 합치거나 순서를 적는다(같은 파일을 두 대화창에서 동시에 고치지 않는다).
- AI 비용이 드는 일(실제 AI 호출, 재분류, 측정)은 「주의」에 호출 수와 예상 금액을 적는다. **하루 기준 $20**(11/23 미리 결정): 작업 대화창은 (필요하면 `/token`으로 오늘 누적을 보고, Sonnet 5.5 $2/$10·Opus 5.5 $4/$20 per 1M) 누적 + 예상 금액이 $20 이하면 금액만 알리고 진행하고, 넘으면 미리에게 승인받는다(나=미리면 내가 정한다). HCX는 대회 크레딧(50만 원, ~12/31, 11/24 수령)에서 빠진다. 단가를 확인하기 전까지는 $에 넣지 못하니 HCX 호출 수·토큰을 함께 보고한다(예상과 누적 모두).
- 지시문 뒤에 한 줄만 남기고 멈춘다: **"위 블록을 새 대화창에 하나씩 붙여 넣어 돌리세요(창마다 블록 위에 적힌 모델로 바꾼 뒤 붙여 넣고 엔터 — 이미 승인돼 있어요). 이 창은 총괄 창으로 남겨 두고, 끝나면 여기서 점검·마무리(밀종료)를 하세요."**
- 보고 맨 끝에 한 줄 더: **「이 창에서 `/loop 20m /milwatch`를 켜 두면 20분마다 PR 메시지·큐·겹침·결정요망을 점검해요.」**
- 이 창에서는 이어서 팀원과 맞출 일·내가 정할 일을 상의한다. **미리만** PR 병합: 미리 승인 뒤에만(`gh pr merge <n> --merge --admin`, hufsiei 계정). 나≠미리면 병합하지 않고 PR 본문 「팀원에게」로 미리에게 `(요청)`을 남긴다.

## 작업 규칙 (늘 지킨다)
- 저장소 수정은 이 창에서 하지 않는다. 내가 이 창에서 고쳐 달라고 직접 말하면 milwork 규칙대로(작업 폴더·상태판 줄) 한다.
- worktree에서도 `.env`·로그는 본 저장소 것을 쓴다(functions/paths.py). `.env`는 절대 읽어서 보여 주지 않는다.
- 파일 패치 스크립트는 Bash heredoc 대신 Write 도구로 파일을 만들어 실행한다(heredoc이 `\`를 망가뜨림).
- 폴더를 지울 때 셸이 그 폴더 안에 있으면 "Device or resource busy"로 실패한다. `cd /c/dev` 후 다시 `rm -rf`.
- 담당 경계는 CLAUDE.md 「누가 무엇을 고치나」를 나 기준으로 본다. 남의 담당 파일을 고쳐야 하면 먼저 그 사람에게 PR 본문 「팀원에게」로 알린다(미리 담당 파일은 미리에게).
- 팀원에게 보낼 글이 필요하면 초안만 쓰고 보내지 않는다.
